# OrientMatch — Gradient-Orientation Template Matching for OpenCV

**日本語** | [English](README.md)

OrientMatch は、密な勾配方向場の相関と姿勢の粗密探索という既存要素を、扱いやすい
C++17/OpenCV ライブラリとしてまとめたものです。再利用可能なマッチャーAPIと、適用条件を
明示した実務指向の実装です。

対応する問題設定は次の範囲です。

- グレースケールの単一テンプレート
- 既知・固定スケール
- 大きいグレースケール画像中の最良一致1件
- 平行移動と面内回転
- CPU実行。OpenMPがあれば角度候補を並列評価

使用する方向場は

```text
z = (gx, gy) / (sqrt(gx^2 + gy^2) + eps)
```

です。2成分の非中心化相関をエネルギーで正規化し、縮小画像上で全位置を疎な角度集合について
探索します。次に、互いに離れた上位候補を残し、走査で飛ばした角度と厳密な姿勢を局所的に
原寸画像で回収します。

## 何を照合しているか

![方向場・ベクトルの回転・内積スコア](./figs/principle.svg)

各画素を長さがほぼ1の勾配方向ベクトルに変換するため、明るさやコントラストではなく形状で
姿勢を評価します。テンプレートを回転するときは、標本位置だけでなくベクトルの値も回転させ
ます。位置だけを回すと、すべての内積が `cos θ` 倍に目減りします。1つの姿勢のスコアは、
その内積をエネルギーで正規化して合計した値です。

## 処理の概要

![OrientMatchの処理パイプライン](./figs/pipeline.svg)

テンプレートの方向場・正方形の回転キャンバス・粗角度の回転テンプレート群は、`Matcher` の
構築時に一度だけ作ります。各フレームでは方向場に変換し、縮小画像上で疎な角度集合について
大域探索を行い、続いて局所的に精密化します。精密化は、まず走査で飛ばした角度を縮小画像上で
試し、次に原寸画像で行います。どの段でも1つの画像窓に対して多数の角度を相関させるため、
窓の変換は一度だけ行って全角度で使い回します。フレームあたりの計算時間の大半は、以前は
ここに費やされていました。図は処理関係を示す模式図であり、固定スケール・最良一致1件という
現在の適用範囲を表しています。

## 位置づけ

これは初期段階の参照ライブラリであり、**新規アルゴリズムやSOTA性能を主張するものでは
ありません。** 勾配方向類似度、回転テンプレート群、画像ピラミッド上の姿勢探索には、
Stegerのshape-based matching、LINE-2D、Konishiらのoriented-gradient matchingなどの
先行研究があります。

本ライブラリの価値は、既存要素を次の形で実装・パッケージ化している点にあります。

- 1枚のテンプレートから回転テンプレート群を構築する、再利用可能な`Matcher`
- 疎な量子化方向ではなく、密な連続2成分方向場
- 勾配強度のソフトゲートと、パッチ全体のエネルギー正規化相関
- OpenCVを使ったCPU実装と、任意のOpenMP角度並列化
- 座標・角度規約、入力検証、テスト、CMakeインストールの明文化
- 固定スケール・最良姿勢1件に絞った小さなAPI

これらは設計空間上の一つの実用的な構成ですが、個々の要素や手法群そのものを新規技術
として提示するものではありません。

コードは [radon-template-matching](https://github.com/hijimasa/radon-template-matching) の
画像空間対照 `ori_img` から独立ライブラリとして抽出したものです。

## 関連実装と選び分け

以下の実装はOrientMatchと一部が重なりますが、表現や対象用途が異なります。

| 実装 | 共通点 | OrientMatchとの主な違い |
|---|---|---|
| [OpenCV `matchTemplate`](https://docs.opencv.org/4.x/de/da9/tutorial_template_matching.html) | 画像空間の密な相関 | 固定テンプレートの平行移動を探索する。回転と粗密探索の組み立ては利用側が行う。 |
| [OpenCV LINEMOD](https://docs.opencv.org/4.x/d7/d07/classcv_1_1linemod_1_1Detector.html) | 勾配方向とテンプレートピラミッド | 選択・量子化した方向特徴を使い、通常は必要な視点・姿勢ごとのテンプレートを登録する。 |
| [`shape_based_matching`](https://github.com/meiqua/shape_based_matching) | C++/OpenCV、勾配方向、ピラミッド、回転・スケールテンプレート | LINEMOD/HALCON系の疎特徴照合で、姿勢テンプレート生成、SIMD、NMSを含む検出寄りの実装。 |
| [OpenCV `GeneralizedHoughGuil`](https://docs.opencv.org/4.x/d3/d20/classcv_1_1GeneralizedHoughGuil.html) | エッジ勾配と位置・回転・スケール推定 | 密な正規化相関ではなく、一般化Hough投票を使う。 |
| [`batchmatch`](https://github.com/wlruys/batchmatch) | 正規化勾配場と変換探索 | PyTorch/FFTを中心としたアフィン格子の一括レジストレーションで、小さなC++局所精密化マッチャーではない。 |
| [`corrmatch-rs`](https://github.com/VitalyVorobyev/corrmatch-rs) | 回転対応の粗密テンプレート探索 | OpenCVの密な勾配方向相関ではなく、Rustで輝度ZNCC/SSDを使う。 |

この一覧は網羅性を主張するものではありません。本ライブラリの実務上の区別は、1枚の
テンプレートを受け取るC++ API、密な連続方向場、正規化相関、位置・回転の粗密探索を
一つにまとめている点です。新しい用途では、どれかが常に高速・高精度と仮定せず、上記の
候補を実データで比較してください。

[`benchmarks/`](./benchmarks) では、直接実行できる手法 — 回転テンプレート群による
`matchTemplate`、方向場ではなく輝度を評価する同一構造の粗密探索、Fourier-Mellin、
ORB/SIFT + RANSAC — と OrientMatch を、Kodak 画像に対する回転・ノイズ・遮蔽・照明変化・
JPEG・スケール不一致の条件で比較しています。要約は下記のとおりで、プロトコルとその限界は
同ディレクトリの README にあります。

### 成功したケースでの精度と計算時間

他に負荷のない22コア機、`OMP_NUM_THREADS=8`。一発はテンプレート準備込み、フレーム毎は
探索のみで、テンプレート毎の準備を外に出した値です。これは本手法だけでなく全手法に
適用しています。

| 手法 | 角度誤差中央値 [度] | 位置誤差中央値 [px] | 一発 [ms] | フレーム毎 [ms] |
|---|---|---|---|---|
| **OrientMatch** | 0.25 | 0.32 | 26.4 | **14.2** |
| 輝度NCC 粗密 | 0.25 | 0.37 | 53.9 | 46.6 |
| 輝度NCC 総当たり1度 | 0.25 | 0.37 | 502.4 | 495.7 |
| Fourier-Mellin | 0.93 | 0.54 | 23.8 | 23.8 |
| ORB + RANSAC | 0.81 | 0.51 | 5.2 | 4.6 |
| SIFT + RANSAC | 0.06 | 0.16 | 17.1 | 15.1 |

真値の角度は小数部を持たせてあるため、1度刻みの精密段で到達できる下限が0.25度です。
相関系の手法はこの量子化限界に張り付いており、精度の限界ではありません。

### 存在と不在の判別

AUC は「存在する場合のスコアが不在の場合を上回る確率」で、別画像からテンプレートを取る
負例条件で測っています。特徴点系はスコアがインライア数なので、行をまたいだ比較は
できません。

| 手法 | AUC clean | AUC ノイズ25 |
|---|---|---|
| **OrientMatch** | 1.000 | **0.999** |
| 輝度NCC 粗密 | 1.000 | 0.922 |
| 輝度NCC 総当たり1度 | 1.000 | 0.923 |
| Fourier-Mellin | 0.640 | 0.624 |
| ORB + RANSAC | 0.825 | 0.741 |
| SIFT + RANSAC | 0.967 | 0.834 |

### この表から読み取れること

最も重要なのは**輝度NCC 粗密**の行です。粗段の解像度・角度テンプレート群・精密化・
候補数まで探索構造は完全に同一で、方向場の代わりに輝度相関を評価します。89.8% 対 97.2%
という差は、したがって探索ではなく評価関数に由来します。総当たり1度も同水準（90.7%）に
留まり、フレーム毎で35倍のコストを払っています。粗密探索が制約になっているわけでも
ないということです。

特徴点マッチングは別種のトレードオフです。SIFT はここで最も**精密**な手法で、相関系の
量子化限界0.25度に対し0.06度と大きく上回り、しかも高速です。ただしテクスチャを必要と
し、ノイズ σ=50 では成功率36%（OrientMatch は96%）まで落ちます。ORB は3倍高速な代わりに
最も当たりません。Fourier-Mellin はこの設定では優位性が全くありませんが、これは
2枚が単一の大域回転で関係づくことを前提にする手法であり、大きなシーンの中の小さな
テンプレートはその前提を満たさないためです。

以上はいずれも測定した設定 — グレースケール単一テンプレート、既知スケール、単一インス
タンス、写真シーン — の外には一般化しません。テクスチャの乏しいテンプレート、複数
インスタンス、未知スケールはすべて対象外です。

## C++ API

```cpp
#include <opencv2/imgcodecs.hpp>
#include <orient_match/orient_match.hpp>

cv::Mat image = cv::imread("search.png", cv::IMREAD_GRAYSCALE);
cv::Mat templ = cv::imread("template.png", cv::IMREAD_GRAYSCALE);

orient_match::MatcherOptions options;
options.coarse_scale = 0.5;
options.coarse_angle_step_deg = 3.0;
options.fine_angle_step_deg = 1.0;
options.refine_top_k = 5;
options.angle_scan_stride = 0;  // 0なら大域走査の角度刻みを自動で決める

// 構築時にテンプレート方向場と粗角度の回転テンプレート群を事前計算する。
orient_match::Matcher matcher(templ, options);
orient_match::MatchResult result = matcher.match(image);

if (result) {
    std::cout << result.center.x << ", " << result.center.y << "\n";
    std::cout << result.angle_deg << " deg, score=" << result.score << "\n";
}
```

### 対象が存在しない場合の判定

既定では `match()` は、どれだけ弱い一致でも必ず最良姿勢を返します。`min_score` を設定すると、
存在するかどうかの判定も行います。

```cpp
options.min_score = 0.6;   // これを下回る姿勢は棄却する
orient_match::Matcher matcher(templ, options);

const auto result = matcher.match(image);
if (result) {
    // 検出
} else if (result.status == orient_match::MatchStatus::below_min_score) {
    // 画像内に対象が無いか、認識できないほど隠れている
}
```

万能の閾値はありません。スコアはテンプレートのうちテクスチャを持つ面積の割合に依存するため、
対象が写っている画像と写っていない画像の両方で `min_score` を較正してください。次の2つの値が
その助けになります。いずれも棄却された結果にも格納されます。

- `MatchResult::score` — 最終的な正規化相関値。
- `MatchResult::margin` — 最良の粗候補が、キャンバス半径以上離れた最良候補をどれだけ上回るか。
  対象が存在すればその位置で明確に勝ち、存在しなければ似たようなピーク同士が拮抗します。

参照シーン（雑然とした背景に、強い偽陽性として鏡像コピーを1つ含む）では、存在時のスコアは
0.76以上、不在時は0.52以下で、その間のどの閾値でも分離できました。最も強い偽陽性は鏡像の
類似物です。スケールが固定であるため、スケール違いの物体は容易に棄却されます。遮蔽に対しては
なだらかに劣化し、25%遮蔽で0.74、50%遮蔽で0.51です。70%遮蔽は不在と区別できません。

`min_score` を設定すると、粗段の最良スコアがその閾値に届き得ない画像では途中で打ち切り、
原寸での処理をすべて省きます。対象が無いシーンではフレーム時間の40%強が削減されます。
打ち切りの積極度は `coarse_gate_ratio` で制御します。その既定値は、参照シーンで実測した
粗スコアと最終スコアの比の下限に対して余裕を持たせてあります。

### 複数インスタンスの検出

`match()` は最良の姿勢を返します。`matchAll()` は調べた別々の場所すべてを、スコア降順で
返します。

```cpp
options.min_score = 0.6;      // 件数を当てにする前に必ず設定する
options.refine_top_k = 8;     // 返りうる最大件数でもある
orient_match::Matcher matcher(templ, options);

for (const orient_match::MatchResult &m : matcher.matchAll(image)) {
    std::cout << m.center << " " << m.angle_deg << " deg, score=" << m.score << "\n";
}
```

`refine_top_k` は探索予算であり、同時に返却件数の上限です。増やせばより多くの場所を調べ、
返せますが、コストも比例します。「別の場所」の判定は2つのパラメータで制御します。

- `candidate_separation` — 粗段で2つの候補が離れているべき距離を、回転キャンバスに対する
  比率で指定します。予算を同一箇所の複数角度ではなく別々の場所に振り分けるための値で、
  ここで決まる距離は下限として効きます。これより近いインスタンスは、重なりの設定に
  かかわらず1件にまとめられます。
- `max_overlap` — 精密化後の姿勢について、より良い姿勢とテンプレート矩形がこの割合
  （IoU）を超えて重なる場合に捨てます。上記の分離と違い、正方形キャンバスではなく検出角度
  における**テンプレート自身の矩形**で測るため、細長いテンプレートが占有していない領域まで
  抑制することがありません。

`min_score` に届くものが無ければ `matchAll()` は空を返します。理由を返すのは `match()` の
側です。`min_score` が既定のままだとスコアによる棄却が起きないため、リストは常に
`refine_top_k` 件まで伸び、末尾は雑音になります。

なお実務上 `max_overlap` が効くのは、実際に重なった別インスタンスよりも、同一物体に対する
重複検出の抑制です。同じテンプレートの2つの複製がこの設定が意味を持つほど重なる場合、
互いの方向場の証拠を壊し合うためです。試験シーンでは、96画素幅のテンプレートを84画素
間隔（重なり12%）で置いた場合は両方とも良好なスコアで検出されましたが、70画素間隔では
隠れた側が0.74から0.32まで落ち、検出として成立しなくなりました。

単一チャンネルのテンプレートマスクも指定できます。

```cpp
orient_match::Matcher matcher(templ, mask, options);
```

マスクが0の画素は除外されます。マスク境界を偽エッジにしないため、勾配計算後にマスクを
適用します。回転で補間されたマスクは、エネルギー正規化の前に二値の支持領域へ戻します。
これにより、マスク境界の補間があってもコサインスコアの範囲を維持します。

インストール後はCMakeから利用できます。

```cmake
find_package(OrientMatch CONFIG REQUIRED)
target_link_libraries(my_program PRIVATE OrientMatch::orient_match)
```

## 座標・角度規約

- 左上画素の中心を `(0, 0)` とするOpenCV座標です。
- `MatchResult::center` は入力画像中のテンプレート中心の絶対座標です。
- 正角度は `cv::getRotationMatrix2D` と同じ反時計回りです。
- 返却角度は `[0, 360)` に正規化します。
- 角度探索範囲は半開区間
  `[angle_start_deg, angle_start_deg + angle_extent_deg)` です。

## アルゴリズム

1. 画像とテンプレートを平滑化し、Sobel勾配を計算する。
2. 各勾配ベクトルを画像適応型のソフトゲートで正規化する。
3. テンプレート方向場にガウシアン窓と任意のマスクを適用する。
4. 縮小画像上で、テンプレート群の `angle_scan_stride` 個おきの角度について全有効位置の
   相関を計算する。画像側の変換は一度だけ行い、走査する全角度で使い回す。また、180度
   離れた2つの角度は支持マスクが一致するため、エネルギー相関を共有する。
5. 上位 `refine_top_k` 件の候補を保持する。ただし、より良い候補からキャンバスの半分以内に
   ある候補は捨てる。これにより各候補が同じ場所の別角度ではなく別の場所になる。
6. 各候補の周囲で、縮小画像のまま、走査が飛ばした角度を試す。
7. 原寸画像上で局所位置と近傍の細角度を探索する。粗段は原寸での最適角度から1〜2ステップ
   ずれ得るため、先頭候補についてはさらに外側の角度まで探索する。
8. 各場所で最良の姿勢を保持する。`match()` はその最大を、`matchAll()` は全てを返す。
   いずれも `min_score` を満たす範囲で。

![位置と回転角の粗密探索](./figs/coarse-to-fine.svg)

スコアは `(x, y, θ)` 上の3次元空間に広がります。大域段は位置・角度のいずれについても粗く
走査し（解像度は半分、角度は4個おき）、以降の段は上位`K`か所の周囲だけを詳しく見ます。
これにより、原寸での総当たり探索に比べて計算量はごく一部で済みます。角度を疎に標本化しても
安全なのは、スコアが角度に対してなめらかに変化するためです。参照シーンでは、64〜500画素の
キャンバスにわたり、12度刻みの走査が総当たり走査と完全に同一の姿勢を再現し、差が現れ始めた
のは24度刻みからでした。ただし高速化のためのヒューリスティックであることに変わりはなく、
狭い大域最大を必ず保持する保証はありません。

3枚の図はいずれも、合成シーンに対してアルゴリズムを実行した結果から生成しています。
生成スクリプトは [`tools/figures`](./tools/figures) にあります。

`Matcher` の構築時に粗角度の回転テンプレート群を作るため、同じテンプレートを複数フレーム
へ繰り返し適用できます。構築後は不変で、`match()` の作業バッファは呼び出しごとに独立
しています。

## 適用範囲と現在の制約

- スケール探索は行わない。
- 複数インスタンスは `matchAll()` で返せるが、2つがどこまで近づけるかは粗段の
  `candidate_separation` が下限を決め、実務上はスコアが制約になる。大きく重なった
  インスタンスは互いの証拠を劣化させる。
- 位置と角度は離散値で、サブピクセル・サブ角度補間は未実装。
- 粗密探索はヒューリスティックであり、真の大域最大を取りこぼさない保証はない。
- 無制限なテンプレート群の確保を避けるため、過剰に細かい角度格子は拒否する。現在の上限は
  粗角度4,096件、細角度オフセット4,097件、1回の照合あたりの精密タスク1,000,000件。
- `coarse_scale`適用後の正方形テンプレートキャンバスは3 x 3画素以上必要。
- スコアは校正済み確率でも、あらゆる入力に共通する検出閾値でもない。`min_score` は
  テンプレートごとに、代表的な正例・負例画像で較正する必要がある。
- テンプレートの正方形回転キャンバス全体が探索画像内に収まる必要がある。
- 精密段では原寸テンプレートを候補角度ごとに回転するため、大テンプレートや広い探索は
  高コストになり得る。
- フレームあたりの処理は演算よりメモリ帯域で律速するため、全コアを使い切る前に
  スループットの改善が頭打ちになる。22コアの試験機では8スレッド前後が最良で、
  それを超えるとフレーム時間はかえって悪化した。
- 現時点では、特徴点ベース照合、学習型検出器、固定スケールを超える一般のアフィン位置
  合わせを置き換えることは目的としていない。
